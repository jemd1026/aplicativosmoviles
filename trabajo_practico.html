Trabajo Práctico

Apps móviles con API REST para la Amazonía peruana. Cada grupo elige un problema real de la región selva y construye una app Android que lista y registra información a través de su propia API PHP + MySQL publicada en un hosting, aplicando lo trabajado en la guía API REST en Android.

3 – 4integrantes por grupo
6 díaspara entregar todo
16proyectos para elegir
20 ptsnota vigesimal + 2 de bonificación
Requisito obligatorio: la API (PHP + MySQL) debe estar publicada en un hosting y la app debe conectarse a ella mediante su URL pública. Un trabajo cuya API funcione solo en localhost, con 10.0.2.2 o con la IP de una PC no pasa a calificación.

1. Contexto y propósito

Loreto, Ucayali, San Martín, Madre de Dios, Amazonas y la selva central concentran más del 60 % del territorio nacional, pero gran parte de su información productiva, turística y de servicios sigue registrándose en cuadernos, hojas sueltas o grupos de WhatsApp. Una app sencilla que consulte y registre datos en un servidor ya resuelve problemas concretos: saber a qué hora sale la lancha, cuánto se pagó por kilo de cacao o dónde se reportó un incendio.

🎯 Competencia

Desarrolla una aplicación móvil nativa que consume una API REST propia para listar y registrar información, con interfaz usable y validaciones.

🌳 Pertinencia

El proyecto debe responder a una necesidad real de la región, con datos verosímiles de la zona (lugares, especies, productos, rutas).

🧩 Base técnica

Se reutiliza la arquitectura de la guía: config.php, listar.php, registrar.php, Retrofit, RecyclerView, formulario y FAB. La diferencia: la API ya no corre en localhost, sino en un hosting con URL pública.

Regla de oro: la guía usa la tabla productos. En el trabajo práctico esa tabla se reemplaza por la entidad de tu proyecto (viajes, acopios, reportes, etc.). Cambia nombres de tabla, carpetas, clases Kotlin, layouts y textos; no se aceptan apps que sigan mostrando “Productos” o “Paracetamol”.

2. Proyectos propuestos

Cada grupo elige un proyecto distinto (no se repiten). La elección se registra en el foro del aula virtual en orden de llegada. Si el grupo desea proponer un tema propio de la selva, debe ser aprobado por el docente el día 1 y cumplir los mismos requisitos.

3. Requisitos técnicos mínimos

Todos los proyectos, sin excepción, deben cumplir lo siguiente. Es la misma arquitectura de la guía, aplicada a otra entidad.

🗄️ Base de datos

  • Base MySQL creada en el hosting (el panel puede añadir un prefijo al nombre)
  • Tabla principal con mínimo 6 campos y id AUTO_INCREMENT
  • Tipos adecuados: DECIMAL, DATE, INT, VARCHAR
  • 10 registros o más con datos verosímiles de la región
  • Script .sql exportado que crea e inserta todo

🐘 API PHP

  • Publicada en un hosting con URL pública (HTTPS de preferencia)
  • config.php con PDO, charset=utf8 y los datos de conexión del hosting
  • listar.php (GET) y registrar.php (POST)
  • Consultas con prepared statements
  • Validación de campos en el servidor
  • Respuesta JSON uniforme: success, message, data
  • Pruebas en navegador o Postman (capturas)

🤖 App Android

  • Paquete propio, p. ej. com.example.rioviaje
  • Retrofit + Gson: modelo, ApiService, RetrofitClient
  • BASE_URL apunta al dominio del hosting (no a 10.0.2.2 ni a una IP local)
  • RecyclerView con layout de ítem propio (≥ 3 datos visibles)
  • Formulario de registro con validaciones
  • FAB que abre el formulario; la lista se recarga en onResume()
  • Mensajes de error si no hay conexión o el servidor falla

Identidad de la app

  • Nombre en strings.xml y ícono propio (Image Asset de Android Studio).
  • Colores del tema relacionados con la temática (verde selva, tonos tierra, azul río…).
  • Textos, hints y mensajes en español, sin restos del ejemplo de productos.
  • Formulario con el tipo de teclado correcto (inputType numérico, decimal, fecha o teléfono según el campo).
Hosting obligatorio: Laragon/XAMPP sirve solo como borrador mientras programan. El control del día 2, el APK, el video y la sustentación se hacen siempre contra la API en el hosting. El docente instalará el APK en un celular con datos móviles: si la app depende de la PC del grupo, el trabajo no se califica.

4. Publicación de la API en un hosting

Este paso es obligatorio: sin API en hosting no hay trabajo que calificar. El hosting debe ofrecer PHP 8 y MySQL/MariaDB con phpMyAdmin. Puede ser un plan gratuito o de pago; el grupo es responsable de que la API esté en línea desde el día 2 hasta la publicación de notas.

Cuidado con algunos hostings gratuitos: varios planes gratuitos (por ejemplo InfinityFree o ByetHost) responden a cada petición con una página de verificación en JavaScript antes de mostrar el contenido. En el navegador se ve bien, pero Retrofit recibe HTML en lugar de JSON y la app falla con Expected BEGIN_OBJECT but was STRING. Antes de elegir, prueba la URL en Postman: debe devolver JSON puro.

Pasos para publicar

  1. Crear la cuenta y un subdominio o dominio, por ejemplo tp-g01-rioviaje.tuhosting.com.
  2. Crear la base de datos MySQL desde el panel y anotar: servidor (host), nombre de la base, usuario y contraseña.
  3. Importar el script .sql en phpMyAdmin del hosting. Quita la línea CREATE DATABASE y USE si el hosting no permite crear bases desde SQL.
  4. Editar config.php con los datos del panel (ver ejemplo).
  5. Subir la carpeta de la API a public_html/ (o htdocs/) con el Administrador de archivos o por FTP con FileZilla.
  6. Probar https://tu-dominio/api/viajes/listar.php en el navegador del celular con datos móviles y registrar.php con Postman.
  7. Cambiar la BASE_URL en RetrofitClient.kt por la URL del hosting y generar el APK.
public_html/                     ← raíz del hosting
└── api/
    ├── config.php               ← datos de conexión del hosting
    └── viajes/
        ├── listar.php           → https://tp-g01-rioviaje.tuhosting.com/api/viajes/listar.php
        └── registrar.php        → https://tp-g01-rioviaje.tuhosting.com/api/viajes/registrar.php
<?php
// Datos que entrega el panel del hosting (sección "Bases de datos MySQL")
$host = "sql123.tuhosting.com";       // en muchos hostings es "localhost"
$db   = "cuenta_tp_g01_rioviaje";      // nombre con el prefijo de la cuenta
$user = "cuenta_tpg01";
$pass = "********";

header('Content-Type: application/json; charset=utf-8');

try {
    $conexion = new PDO("mysql:host=$host;dbname=$db;charset=utf8", $user, $pass);
    $conexion->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
} catch (PDOException $e) {
    http_response_code(500);
    echo json_encode([
        "success" => false,
        "message" => "No se pudo conectar a la base de datos"
    ]);
    exit;
}
En un servidor público no muestres $e->getMessage() al cliente: puede revelar el usuario o el host de la base de datos. Devuelve un mensaje genérico, como en el ejemplo.

HTTP o HTTPS

Con HTTPS (recomendado)

La mayoría de hostings ofrece SSL gratuito (Let's Encrypt). Usa https:// en la BASE_URL y ya no necesitas permitir tráfico HTTP en la app.

Solo HTTP

Mantén network_security_config.xml, pero autoriza el dominio del hosting en lugar de 10.0.2.2.

Siempre

Permiso INTERNET en el Manifest y la BASE_URL terminada en /; si no, Retrofit lanza una excepción al iniciar.

package com.example.rioviaje.api

import okhttp3.OkHttpClient
import okhttp3.logging.HttpLoggingInterceptor
import retrofit2.Retrofit
import retrofit2.converter.gson.GsonConverterFactory
import java.util.concurrent.TimeUnit

object RetrofitClient {
    // URL pública del hosting. Debe terminar en "/".
    private const val BASE_URL = "https://tp-g01-rioviaje.tuhosting.com/api/"

    val instance: ApiService by lazy {
        val logging = HttpLoggingInterceptor().apply {
            level = HttpLoggingInterceptor.Level.BODY
        }

        // Un hosting compartido puede tardar más que localhost en responder
        val client = OkHttpClient.Builder()
            .addInterceptor(logging)
            .connectTimeout(20, TimeUnit.SECONDS)
            .readTimeout(20, TimeUnit.SECONDS)
            .build()

        val retrofit = Retrofit.Builder()
            .baseUrl(BASE_URL)
            .client(client)
            .addConverterFactory(GsonConverterFactory.create())
            .build()

        retrofit.create(ApiService::class.java)
    }
}
Los endpoints de ApiService son relativos a la BASE_URL: con la URL anterior, @GET("viajes/listar.php") llama a https://tp-g01-rioviaje.tuhosting.com/api/viajes/listar.php.
Atención con los tipos: PDO devuelve los DECIMAL e INT como texto ("120.00"). Gson suele convertirlos sin problema, pero si ves errores de conversión, castea en PHP ((float)$fila['precio']) o declara el campo como String en Kotlin y conviértelo al mostrarlo.

En hosting, GET y POST funcionan; falta validación o el JSON no es uniforme. En hosting funciona solo uno de los dos endpoints. La URL pública no responde o concatena SQL sin preparar.
3. Retrofit y modelos3 Modelo, ApiService y RetrofitClient correctos, @SerializedName donde corresponde, llamadas asíncronas con manejo de onFailure. Funciona contra el hosting, pero sin manejo de errores de red. Funciona parcialmente contra el hosting (solo lista o solo registra). No consume la API.
4. Listado (RecyclerView)3 Ítem propio con ≥ 3 datos y formato (moneda, fecha), adapter limpio, recarga tras registrar. Lista correcta con diseño básico. Lista con datos incompletos o sin recargar. No muestra datos.
5. Registro (formulario + FAB)3 FAB abre el formulario, validaciones (vacíos, números, rangos), inputType adecuados, mensaje de éxito y regreso a la lista. Registra correctamente con validaciones mínimas. Registra sin validar o con errores frecuentes. No registra.
6. Pertinencia regional y UX2 Problema real bien sustentado, datos de la zona, ícono, colores y textos coherentes con el tema. Tema adecuado con identidad visual básica. Restos del ejemplo de la guía (productos). Sin relación con la región.
7. Informe y video1 Informe completo según estructura y video claro dentro del tiempo. Falta una sección o el video excede el tiempo. Informe o video incompletos. No entrega.
8. Sustentación individual2 Explica y modifica su parte del código con seguridad. Explica con apoyo del grupo. Explica de forma superficial. No puede explicar el código.

Penalidades

  • Entrega tardía: −2 puntos por día, hasta un máximo de 2 días; después no se recibe.
  • Archivos incompletos o que no abren: se califica solo lo que se puede ejecutar.
  • API solo en localhost, con 10.0.2.2 o con IP local: el trabajo no pasa a calificación (no se aplica la rúbrica).
  • Hosting caído o suspendido al momento de la revisión: se califican los criterios 2 a 5 solo con lo demostrado en la sustentación. Mantengan la cuenta activa hasta la publicación de notas.
  • Copia entre grupos o código ajeno sin citar: nota 0 para todos los grupos involucrados.
  • Integrante que no sustenta: obtiene 0 en el criterio 8 y su nota técnica puede reducirse según su participación declarada.
